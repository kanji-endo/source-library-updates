## 1. 結論

1. **`latest.json` の `url` が仮の値（`https://booth.pm/ja/items/0000000`）のまま公開ブランチに載っている。** 次に `version` を上げる時に `url` の差し替えを忘れると、全ユーザーに存在しない商品ページへの案内が出る。版を上げる前に必ず直す必要がある。
2. **このファイルは全ユーザーのアプリが信用する「配信経路」なのに、書き込み側の安全網が無い。** `main` にブランチ保護・ルールセットが無く、CI も無い。壊れた JSON・不正な版番号・BOOTH 以外の URL をそのまま公開できてしまう。
3. **改善の中心は「公開前の自動検査」1本で足りる。** JSON Schema（版番号の形式、`url` の許可パターン、仮 ID の拒否）を GitHub Actions で検査し、ルールセットで必須チェックにする。工数は半日以下。
4. **アプリ側の前提（取得失敗時の挙動、版の数値比較、URL のホスト検査）は、このリポジトリからは確認できない。** 2025-05 以降の GitHub の未認証アクセス制限で取得に失敗し得るため、アプリ側で「失敗したら黙って何もしない」ことを確認したい。
5. **良い点**: README が短く、役割・各項目の意味・URL 制限が1画面で分かる。アプリ本体を置かない設計で、乗っ取られても誘導先が BOOTH に限られる（アプリ側の検査が正しければ）。シークレットスキャンとプッシュ保護は有効。

## 5. 進め方の提案

- **第1段: 文書と検証の仕組み**（30分〜1時間）
  - `url` の仮値を直す（アプリ公開前に必須）。
  - README にリリース手順と取り消し方を追記。
  - `schema/latest.schema.json` と、それを検査する GitHub Actions ワークフロー（`pull_request` と `push` で実行）を追加。手元でも同じ検査を1コマンドで回せるようにする。
- **第2段: 安全網**（15〜30分）
  - ルールセットで削除・強制プッシュを禁止し、検査を必須ステータスチェックにする。
  - 2FA を確認し、Wiki・Projects を閉じる。
  - フックや自作エージェントは不要。持ち主の「半年ごとに CLAUDE.md・スキル・フックを外して素の挙動を見る」方針とも衝突しない。検査は GitHub 側の CI に置くので、Claude Code の設定を外しても残る。
- **第3段: ホットスポット解消**
  - このリポジトリでは該当なし。残る課題はアプリ本体側（取得失敗時の挙動、版比較、URL 検査、`notes` の描画）で、アプリのリポジトリの調査で扱う。
